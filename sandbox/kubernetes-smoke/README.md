# Official KIND workflow validation

The tracked official-kind.mjs fixture refuses real project IDs. Run it only in a new recorded scripts/kubernetes-lab.mjs sandbox. It verifies bare base startup, opt-in CNPG installation, two independent PostgreSQL/app environments, directly loaded images, dirty-source isolation, failed Job detection and UID-safe cleanup. It builds a small SQL client fixture; it is not the Monorepo application acceptance suite.

No Argo CD, Kargo, Git service, OCI promotion artifacts or local registry are installed. The host wrapper must verify the exact sandbox ID before each operation and remove only that owned test VM. Keep kubeconfigs and Secret values in the guest. Record sanitized receipts under ignored .artifacts/kind-direct. Cold restart should use the installed interactive startup hook and verify retained node/namespace/database/Secret identities and database contents.

The k3s/K3sCompat.csproj acceptance fixture uses the official Testcontainers.K3s 4.16.0 module with no custom device mount or entrypoint. In an owned disposable sandbox, install the plugin prerequisites independently of KIND, set TECK_K3S_IMAGE to an explicit compatible K3s image, save a local pod image to /tmp/teck-k3s-pod-image.tar, and set TECK_K3S_POD_IMAGE to that image's name. Run the fixture as agent with the normal terminal startup hook. It checks the inherited character device, Ready node, a completed pod with exact output, and API readiness after scheduling; it disposes its K3s container. Repeat after a cold sandbox restart and verify the existing KIND node/pod identities separately. This does not validate CNPG/Barman backups, WAL recovery, external registry access inside K3s, or mesh compatibility.

devices.mjs runs the real shared helper in a disposable privileged child container using an explicit digest-pinned KIND node image. It verifies concurrent/idempotent creation and refusal to overwrite a regular file, directory, symlink or wrong character device. It refuses non-isolated project IDs and never alters the VM's /dev entries for the negative cases.
